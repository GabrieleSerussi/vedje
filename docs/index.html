VEDJE: Video-Efficient Discriminative Joint Encoder for Scalable Video-Text Retrieval

VEDJE moves video encoding offline and keeps joint matching online. A 33M-parameter joint encoder reranks the candidates from a small cache written once per video.

  • ResultOn MSR-VTT, VEDJE improves R@1 over each matched first stage by 3.6 to 7.2 points, across both retrieval directions. With a fine-tuned VideoCLIP-XL first stage, it matches the LamRA reproduction in text-to-video R@1 with about 49 times fewer online parameters.
  • WhyEach cache is written before any query arrives, so it must hold evidence for every action and moment a query might describe. VEDJE does this by keeping a separate token group for each sampled frame.
  • StorageThe default cache takes 48 KiB per video, 128.5 times smaller than the frame-and-patch features. In the VideoPrism configuration on MSR-VTT, a fourfold smaller cache keeps text-to-video R@1 within 0.2 points of it.

Overview · how it works

Compact per-frame evidence, computed once per video, lets a small joint encoder verify each candidate against the query.

  • CacheEach sampled frame is compressed into a few learned tokens. The tokens stay in temporal order, so the cache keeps a separate group for each sampled frame.
  • ChangeDuring training, a head predicts from each frame's tokens how its features change a few sampled frames later. The head is then discarded, so it adds no work at query time.
  • RerankA 33M joint encoder reads the query next to each candidate's cache. The first-stage score is added to its output, and the candidates are sorted by the final score.

02 · How it works

VEDJE moves video encoding offline and keeps a separate token group for each sampled frame.

Section 3 of the paper, with Figure 2 and Appendices A.1 to A.3.

Finding the right video often means telling apart similar scenes in which different events occur. Joint matching of the query and the video improves retrieval, but processing rich video features for every query is costly. VEDJE encodes each video once, compresses each sampled frame into a few tokens and lets a small joint encoder read them at query time.

The VEDJE pipeline, step by step.

03 · Use it

Index your own videos and rerank them with the released code.

Code by the authors. The recipe follows Sections 3 and 4.1 and Appendices A.1 to A.3 of the paper.

You need videos with captions and a GPU for training. One command trains VEDJE on any of the four datasets, and two more index your own videos and search them with text. The Colab notebook indexes a clip of your choice and times a query against a typical reranker, on a free CPU runtime.

GitHub: vedje Open the Colab tour
  1. Index. Run the frozen visual encoder once per video and keep its frame-indexed features.
  2. Prepare the first stage. Embed the training videos and captions with the first-stage retriever, and mine hard negatives from its rankings.
  3. Train. Train the compressor, the joint reranker and the training-only heads together.
  4. Rerank. Write each video's cache once. For each query, rerank the first stage's candidates from their caches.
Open source

Rerank your own collection.

Clone the repository and train VEDJE with one command. Two more commands, or a few lines of Python, index your videos once and search them with text.

Open on GitHub 
# 1. clone and install (Python 3.10 or newer)
git clone https://github.com/GabrieleSerussi/vedje.git && cd vedje
pip install -e .

# 2. train on a GPU
vedje train configs/vedje_vp_msrvtt.yaml

# 3. index your videos once, then search them with text
vedje index output/vedje_vp_msrvtt/checkpoint_03.pth my_videos/ --out my_index.pt
vedje search my_index.pt "a person walks across a field"
04 · Details

What the cache keeps, and what each part adds.

Sections 4.3 to 4.7 of the paper, with Tables 3 to 6 and Appendix Table 11.

Separate frame groups beat pooled caches at the same storage.

The pooled caches and the per-frame cache each hold 64 tokens from the same features, read by the same reranker. Keeping one token group per sampled frame raises R@1 by 2.0 points in both directions over attention pooling. Feature-change supervision then raises it further.

R@1 gain over attention poolingTable 4 · MSR-VTT · 48 KiB caches · longer is better

Feature-change supervision improves R@1 at both cache sizes.

The comparison trains the same model with and without the training-only head. In text to video, the gain grows from 0.6 points with four tokens per frame to 1.9 points with one token per frame.

R@1 gain from feature-change supervisionTable 3 · MSR-VTT · R@1 points · longer is better

On the same cache, the joint encoder scores better than trained MaxSim.

Both scorers read the same cache and candidates, with the first-stage score as input. The first-stage score and the joint features complement each other: either alone reaches at most 50.1, and together they reach 54.6.

Text-to-video R@1 gain over the VideoPrism first stageTable 5 · MSR-VTT · same cache and candidates

Papers: MaxSim

With caches in host memory, a complete query takes under 11 ms with 200 candidates, and under 7 ms with the 12 KiB cache.

Both cache sizes cost about the same at 20 candidates, since text encoding and search are shared. With more candidates, the smaller cache is faster: at 200 candidates its latency is 33% lower.
